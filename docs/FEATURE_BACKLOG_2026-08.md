# 신규 기능 백로그 — 지도·알림 (2026-08-02 기준)

> **성격**: 이 문서는 결함 수정이 아니라 **신규 기능 추가** 할 일 목록이다. 결함·기술부채는
> `docs/IMPROVEMENT_PLAN_2026-08.md`(P0/P1/P2)가 SSOT이고, 이 문서는 그와 별개로 "아직 없는
> 기능을 새로 만드는" 트랙만 담는다. 항목이 착수되면 상태를 갱신하고, 완료되면 이 문서에서
> 지우거나 완료 섹션으로 옮긴다 — 살아있는 체크리스트로 유지.
>
> **선행 조사 근거**: 2026-08-02 신규 기능 발굴 워크플로우(4관점 병렬 발산 + 냉정 검증,
> 우선순위 Top 12 중 6~9위). "바로 만들 수 있는 것"(1~5위, 계산기 프리필·비교 세금열 등
> 기존 데이터 재조합)과 "돈 버는 방법"(10~12위, 제휴·광고)은 이 문서 범위 밖 —
> 그 항목들이 필요해지면 별도 문서로 신설.

## 착수 순서 판단 기준

두 항목 다 "사용자가 확실히 원하지만 코드량이 더 필요한" 급으로 같은 등급이었다. 아래 순서로
진행을 권장하되, 최종 순서는 사장님 판단.

1. **지도 뷰 먼저 권장** — 미분양 쪽에 이미 완성된 `MbClusterMap` 등 지도 컴포넌트 자산이
   있어 재사용 여지가 크고(0→1이 아니라 이식), 경쟁 서비스 대비 "기본기 없음"에 해당해
   없으면 이탈로 직결. 알림은 인프라(발송 채널)부터 새로 결정해야 해서 선행 논의가 더 필요.
2. 알림 시스템은 **발송 채널 결정**(이메일 vs 카카오 알림톡 vs 텔레그램 등)이 선행 조건이라,
   지도보다 "착수 전 결정할 것"이 하나 더 많다. 아래 항목 2의 미결 사항 참조.

## 항목 1 — 매물 검색 결과 지도 뷰

### 무엇을

지금 미분양(`/mibunyang`)엔 지도 보기가 있는데(`MbClusterMap`, list↔map 토글), 정작 서비스의
핵심인 매물 검색(`/search`가 흡수된 홈 검색)·단지 목록엔 지도가 아예 없다. 검색 결과를 지도
위에서 보고, 클러스터로 묶인 마커를 클릭하면 단지 정보가 뜨는 화면을 추가한다.

### 왜 (사용자 가치)

- 호갱노노·직방·다방 등 경쟁 서비스는 전부 기본으로 제공하는 기능 — 없으면 "이 앱은 기본기가
  없다"는 인상으로 이탈 요인이 된다.
- 텍스트 목록만으로는 "이 동네 어디쯤 매물이 몰려 있나"를 파악하기 어렵다. 위치 기반 판단은
  지도가 압도적으로 빠르다.

### 왜 지금 없나 (원인, 결함 아님)

미분양 쪽 지도는 세션 315~316에서 신설됐고 매물 검색 쪽은 그 이전부터 텍스트 목록·테이블
UI로 설계돼 있었다 — 우선순위가 밀렸을 뿐 기술적으로 막힌 이유는 없다.

### 실행 계획 (박제)

- [ ] **1단계 — 재사용 가능성 실측**: `frontend/src/components/mb/MbClusterMap.tsx`·
      `MbLocationMap.tsx`·`MbInfraOverlay.tsx`·`MbMapToolbar.tsx`·`MbViewToggle.tsx` 코드를
      직접 읽어, 미분양 전용 데이터 구조(`apartments`/`unsold_history` 좌표)에 얼마나
      결합돼 있는지 확인. `Complex`(estate) 타입과 `MbApartment` 타입의 좌표 필드명이
      같은지(`latitude`/`longitude` — `.claude/rules/infra.md`가 이미 "naver-estate-web은
      latitude/longitude, mibunyang은 lat/lng" 컬럼명 불일치를 명시함) 먼저 확인해야
      이식 범위를 정확히 잡을 수 있다.
- [ ] **2단계 — 데이터 모집단 크기 확인**: 미분양(수백 단지)과 달리 매물 검색 결과는 최대
      수십~수백 건(필터에 따라 다름)이라 클러스터링 파라미터를 다시 튜닝해야 할 수 있음.
      `complexes` 테이블에서 좌표가 NULL인 비율을 실측(향후 SELECT COUNT 쿼리로, 지도에
      안 뜨는 단지가 얼마나 되는지 미리 파악).
- [ ] **3단계 — UI 배치 결정**: `/search`(홈 흡수형) 결과 화면에 list↔map 토글을 어디에
      둘지(미분양의 `MbViewToggle` 패턴 참고), `mb_view_mode`(localStorage 키, 이미 있음)
      옆에 `article_view_mode`(이미 있음)와 별개로 새 localStorage 키 추가할지 결정.
- [ ] **4단계 — 구현**: 지도 컴포넌트 이식 + 클러스터 마커 + 단지 클릭 시 정보 팝업.
      네이버 지도 SDK는 이미 `NEXT_PUBLIC_NAVER_MAP_CLIENT_ID`로 연동돼 있음
      (`docs/NAVER_MAP_KEY_SETUP.md` 참조) — 새 키 발급 불필요.
- [ ] **5단계 — 회귀 테스트**: 지도 렌더링 정상 케이스 + 좌표 없는 단지 처리(에러 케이스).
- [ ] **6단계 — 커밋 전 검증**: `npx tsc --noEmit` + `npm run lint` + `npx vitest run`.

### 난이도·리스크

보통. 네이버 IP 차단 방지 제약과는 무관(지도는 순수 프론트 렌더링, 추가 네이버 API 호출
없음 — 단지 좌표는 이미 DB에 있음). 회귀 위험은 낮음(신규 화면 추가, 기존 목록 뷰는 그대로).

## 항목 2 — 관심 단지 가격 변동 알림

### 무엇을

즐겨찾기(`favorite_complexes`, 현재 localStorage 전용)에 담긴 단지의 가격이 변동되면
사용자에게 알려주는 기능. 최소 버전은 "재방문 시 변동 배지 표시"(서버 인프라 불필요),
확장 버전은 이메일/카카오 알림톡 등 능동 발송.

### 왜 (사용자 가치)

지금은 사용자가 즐겨찾기 페이지에 직접 재방문해야만 가격이 바뀐 걸 알 수 있다(pull 모델).
관심 단지를 계속 지켜봐야 하는 실사용자·공인중개사 입장에서는 "바뀌면 알려주는"(push 모델)
쪽이 훨씬 가치 있다 — 재방문 유도 효과도 있음.

### 왜 지금 없나 (원인, 결함 아님)

관리자용 텔레그램 알림 인프라(`crawler/monitor.py`, 장애 감지용)는 이미 있지만, **사용자向
알림 채널**(이메일 발송·카카오 알림톡 등)이 설계된 적이 없다. `favorite_complexes`가
localStorage 전용이라 애초에 "서버가 이 사용자가 무엇을 즐겨찾기했는지" 알 방법도 없다
(로그인 사용자와 연결된 서버사이드 즐�지찾기 테이블 부재).

### 미결 사항 (착수 전 결정 필요 — 사장님 판단)

- [ ] **발송 채널**: 이메일(이미 SMTP 인프라 있음, `backend/.env.example`의
      `SMTP_HOST`/`SMTP_USER` 등 — 공인중개사 검증 알림 메일에 이미 사용 중)을 재사용할지,
      카카오 알림톡(신규 계약·비용 발생)을 쓸지, 아니면 최소 버전(재방문 시 배지만)으로
      먼저 시작할지.
- [ ] **즐겨찾기의 서버 이전 여부**: 지금 `favorite_complexes`는 브라우저에만 저장돼
      기기 간 동기화가 안 됨(`.claude/rules/codes.md`에 명시된 기존 설계). 알림을 보내려면
      최소한 "로그인한 사용자가 즐겨찾기한 단지"를 서버 DB에 저장해야 하므로, 이건 단순
      기능 추가가 아니라 **기존 localStorage 설계를 서버 동기화로 바꾸는** 더 큰 결정이다.
      즉시 결정 필요.

### 실행 계획 (박제, 발송 채널 결정 후 착수)

- [ ] **1단계 — 스키마 설계**: 즐겨찾기를 서버로 이전한다면 `user_favorites`(user_id,
      complex_no) 신규 테이블 + 마이그레이션 V040 작성. `backend/CLAUDE.md`의 DB 마이그레이션
      표에 신규 행 추가 필수(release.md 트리거 — DB 마이그레이션은 4중 cross-check 대상).
- [ ] **2단계 — 변동 감지 로직**: `complex_price_history`에 매주 쌓이는 시계열 데이터에서
      "지난 수집 대비 변동" 계산. 신규 스케줄러 잡이 아니라 **기존 `collect_prices`
      잡(수요일 04시) 완료 후 후처리**로 붙이는 것이 스케줄러 잡 신설보다 안전(infra.md
      스케줄러 표에 새 행 추가 필요 여부는 이 설계에 따라 갈림).
- [ ] **3단계 — 최소 버전 먼저 구현**: 발송 채널 결정 전에도 "즐겨찾기 페이지 재방문 시
      변동 배지"는 순수 프론트 계산(서버 알림 인프라 0)으로 먼저 낼 수 있음 — 신규 기능
      발굴 조사에서 "배관 공사 수준"으로 분류된 항목. 이걸 1차로 내고, 능동 발송은 2차로
      분리하는 것을 권장.
- [ ] **4단계 — (발송 채널 확정 시) 알림 발송 인프라**: SMTP 재사용이면 기존
      `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` 그대로, 발송 실패 시 `logger.warning`
      best-effort 패턴(세션 340의 "알림 삼킴 로그화" 관례 답습 — 결제·크롤 알림처럼
      알림 실패가 핵심 로직을 깨면 안 됨).
- [ ] **5단계 — 회귀 테스트**: 변동 계산 로직 단위 테스트(정상 케이스 + 변동 없음 케이스) +
      (발송 채널 있으면) 발송 실패 시 조용히 넘어가는지 테스트.
- [ ] **6단계 — 커밋 전 검증**: BE `ruff check . && python -m pytest`, FE 관련 변경 있으면
      `npx tsc --noEmit && npm run lint && npm test`.

### 난이도·리스크

보통~어려움(최소 버전은 쉬움). 네이버 IP 차단 방지와는 무관(변동 감지는 기존 수집 데이터
후처리, 신규 네이버 호출 없음). **즐겨찾기의 서버 이전은 기존 설계(브라우저별 독립,
`.claude/rules/codes.md` 명시)를 바꾸는 결정**이라 착수 전 반드시 사장님 확인 필요 — 이
문서의 "미결 사항"이 실행 계획보다 먼저 해결돼야 함.
